## Адаптивность \*

- Свойства **обертки**, которые позволяют переносить элементы на новую строчку, если предыдущая заполнилась (**flex-wrap**), а также задают отступы между соседними элементами сверху и снизу (**gap**).
- Свойства **самой карточки**: в данном случае нас интересует первое свойство **flex**, а точнее последнее значение в нем. Это значение определяет, в какой момент элементы переносятся на новую строчку, а именно если размер элемента становится равным **300px**.

*Иллюстрация: адаптивная сетка карточек товаров (Flutter adaptive app).*

```html

  <div class="card__item">

    </div>
    <div class="card__info">
      <div class="card__text">

        <div class="card__description">Описание книги</div>
      </div>

    </div>
  </div>
</div>
```


## Виды нативных приложений \*

- **Нативное приложение** (native app) – прикладная программа, которая разработана для определенной платформы или для определенного устройства.
- **Мобильное приложение** (mobile app) — прикладная программа, предназначенная для работы на смартфонах, планшетах и других мобильных (портативных, переносных, карманных) устройствах, собирается отдельно для iOS или Android.
- **Десктопное приложение** (desktop app) — программа, которая устанавливается на компьютер пользователя и работает под управлением операционной системы, собирается отдельно для macOS, Windows, Linux.

## PWA. Service Worker \*

- Service Worker позволяет закэшировать в браузере (жестком диске) часть файлов-документов.
- Например, можно сохранить файлы приложения или большой файл нейросетевой модели.

Регистрируем service worker, делаем это в файле `index.js` после рендера корневого компонента:

```js
if ("serviceWorker" in navigator) {
  window.addEventListener("load", function() {
    navigator.serviceWorker
      .register("/serviceWorker.js")
      .then(res => console.log("service worker registered"))
      .catch(err => console.log("service worker not registered", err))
  })
}
```

Создаем файл `serviceWorker.js` и кладем его в директорию `public`:

```js
self.addEventListener('fetch', () => console.log("fetch"));
```

## Electron. WebView

- **Electron** — фреймворк, разработанный GitHub.
- Позволяет разрабатывать нативные графические приложения для операционных систем с помощью веб-технологий, комбинируя возможности Node.js для работы с back-end и браузера Chromium.
- **WebView** – компонент, позволяющий использовать веб (верстку, стили, код JS) внутри приложений.

*Схема:* Chromium (for making web pages) + Node.js (for filesystems and networks) + Native APIs (for three systems) = **Electron**.
Архитектура: несколько окон *Window* (HTML, CSS, JS (DOM) + Node) связаны по **IPC** с *Main / browser process* (Blink, V8 и т.д. + Node), который через Native APIs обращается к *Operating system*.

## Webhook \*

- **Webhook** – технология, очень похожая на JSON-RPC между серверами для определенных видов запросов, которая появилась в 2007 году.
- Смысл заключается в обратном вызове, когда вызываемый нами сервер должен вызвать наш метод или третий сервер.
- Для Webhook используются отдельные библиотеки, дополнительные действия, и в курсе мы их не используем.
- Вместо этого мы реализуем похожее простое взаимодействие, но с помощью обычного JSON-RPC.
- В данном примере «сайт» – это **вся наша текущая система** с бэкендом и фронтендом.
- Он вызывает сервис уведомлений, но **не ждет, пока тот** отправит уведомление.

*Схема:* Личный сайт (кто-то оставил заявку) → Вебхук `.../alert` → Сервис уведомлений (отправляет уведомление в мессенджер) → API мессенджера (отправляет сообщение) → Мобильник → пользователь.

## DMZ

- **DMZ** (Demilitarized Zone) – сегмент сети, содержащий общедоступные сервисы и отделяющий их от частных.
- Разделение производим с помощью **firewall**.

*Схема «DMZ network architecture»:* Enterprise LAN — Firewall — DMZ Network (Router, Web server, Mail server) — Firewall — Internet.

---

## Как выглядит «DMZ» у нас? \*

- У нас основной **веб-сервис** (скорее **реверс-прокси**) доступен извне – это хороший пример DMZ, остается только его оградить с помощью firewall.
- Мы это не делаем, но подразумеваем, что эти сетевые настройки есть.
- Таким образом все наши критичные **данные** (БД, Redis) и **асинхронный сервис** недоступны извне.
- Но вот для обратного вызова от асинхронного к **основному** мы должны добавить какую-то **аутентификацию**.

*Схема:* Интернет (пользователи или злоумышленники, веб-браузер) — firewall — **DMZ Web Сервер** (Основной веб-сервис) — firewall — **Внутренний Web сервер** (Асинхронный сервис, PostgreSQL).

---

## Sequence для асинхронного метода \*

- При формировании заявки **(1)** мы обращаемся к асинхронному сервису **(2)** и сразу получаем ответ на фронтенде **(4)** – заявка сформирована.
- Но запись результата в БД будет только через время отдельным вызовом **(7)**.
- На фронтенде результат мы получим только когда сами спросим **(9)** об этом.
- Запросы GET **(5)** и **(9)** аналогичны – это Polling из ДЗ.
- На своей диаграмме вы **(5)** и **(6)** не указываете, мы это только подразумеваем.
- Для псевдо аутентификации-авторизации используем **ключ-токен для ОСНОВНОГО сервиса в DMZ** в запросе **(7)**.

*Диаграмма последовательности (веб-браузер / основной веб-сервис / асинхронный сервис):*

| № | Направление | Сообщение |
|---|---|---|
| 1 | Браузер → Основной | `PUT api/request/form(id черновика)` |
| 2 | Основной → Асинхронный | `POST calc(id черновика)` |
| 3 | Асинхронный → Основной | `200` |
| 4 | Основной → Браузер | `200` |
| 5 | Браузер → Основной | `GET api/request` |
| 6 | Основной → Браузер | JSON списка заявок |
| 7 | Асинхронный → Основной | `PUT api/request/result(id заявки, результаты, токен)` |
| 8 | Основной → Асинхронный | `200` |
| 9 | Браузер → Основной | `GET api/request` |
| 10 | Основной → Браузер | JSON списка заявок с результатами |

## Код лабораторной. Асинхронный сервис

- В нем будет один метод `/exchange_async`.
- Данный метод будет запускать отложенное действие.

```python
@router.post("/exchange_async")
async def submit_request(data: dict, background_tasks: BackgroundTasks):

        send_exchange_result_async,
```

## Асинхронное взаимодействие \*

В качестве **достоинств** можно выделить:

- хорошее использование вычислительных ресурсов серверов (никто не простаивает);
- избегание длительных задержек у пользователя;
- при генерации кода через LLM (как и для микросервисов) мы ограничиваем контекст кодом отдельных сервисов (**тратим меньше** токенов).

Как **недостаток**:

- сложность в разработке, особенно когда таких вызовов становится много и они начинают влиять друг на друга;
- пиковые нагрузки на сервера;
- необходимость добавления real-time web для фронтенда для получения изменений в данных.

---

## Решение проблем асинхронности \*

- Использование WebSocket, Long Polling, Short Polling и других технологий **на фронтенде для обновления** данных на клиенте.
- Выделение отдельных сервисов-обработчиков (деление на микросервисы) под каждое выполняемое действие-преобразование данных для сокращения зависимостей.
- Использование брокеров и очередей для избегания пиковых нагрузок.

*Иллюстрация: real-time чат на Spring WebSocket и Angular.*

## Шлюз/брокер сообщений \*

- **Redis** – резидентная база данных
- **Apache Kafka** – брокер сообщений
- **RabbitMQ** – брокер сообщений

*Схема:* producer → server (очередь) ⇄ consumer (push vs pull).

- У нас есть LLM и **много пользователей хотят одновременно** ее использовать, поэтому нам нужно выстроить к ней **очередь** (слово **server** на схеме).
- В веб-приложениях очереди часто используются для отложенной обработки событий или в качестве временного буфера между другими сервисами, тем самым защищая их от всплесков нагрузки.

## Как реализовать взаимодействие между двумя сервисами \*

- Сервисы могут обращаться друг к другу просто по HTTP – хорошо для простых решений (в **нашем курсе**). А можно использовать gRPC.
- В LLM у вас есть основной веб-сервис и асинхронный с LLM. LLM генерирует данные **в потоке** (по несколько слов) и, конечно, **двунаправленно**.
- **gRPC** (Remote Procedure Calls) — это система удалённого вызова процедур (RPC) с открытым исходным кодом, первоначально разработанная в Google.
- В качестве транспорта используется HTTP/2, в качестве языка описания интерфейса — Protocol Buffers.
- gRPC предоставляет такие функции, как аутентификация, двунаправленная потоковая передача и управление потоком, блокирующие или неблокирующие привязки, а также отмена и тайм-ауты.

## Варианты real-time для фронтенда \*

- **Short Polling** – самый простой вариант, просто запросы по таймеру.
- При **long polling** сервер задерживает у себя запрос до возникновения события.
- **Server-Sent Events** позволяет получить несколько ответов от сервера в разные моменты времени вместо одного (**ответы GPT**).
- **WebSocket** – полноценный двунаправленный обмен с сервером.

*Схемы:* сравнение Short polling vs Long polling; XHR polling (`GET /poll`), SSE (`GET /sse`, EventSource protocol), WebSocket (`GET /ws`, WebSocket protocol).

## Реализация Polling \*

- Есть разные реализации **short polling**.
- Одна из самых простых – сделать рекурсивный таймер, по истечении которого мы будем выполнять запрос и новый таймер.

```js
let apiTimeout = setTimeout(fetchAPIData, 1000);

function fetchAPIData(){
    fetch('API_END_POINT')
    .then(res => {
            if(res.statusCode == 200){
                // Process the response and update the view.
                // Recreate a setTimeout API call which will be
                apiTimeout = setTimeout(fetchAPIData, 1000);
            }else{
                clearTimeout(apiTimeout);
                // Failure case. If required, alert the user.
            }
    })
    .fail(function(){
         clearTimeout(apiTimeout);
         // Failure case. If required, alert the user.
    });
}
```

## WebSocket \*

- Протокол связи поверх TCP-соединения, предназначенный для обмена сообщениями между браузером и веб-сервером, используя постоянное соединение.
- Во время установления соединения нам нужно **связать это подключение** с пользователем/чатом:
- не нужно отправлять все уведомления из системы, а только этого пользователя (но на все его устройства).

*Схема жизненного цикла соединения (Client ⇄ Server):*

1. **"CONNECTING" state** — Opening handshake: HTTP "Upgrade" request → HTTP 101 "Switching Protocols"
2. **"OPEN" state** — Data transfer: обмен Data frame в обе стороны
3. **"CLOSING" state** — Closing handshake: "Close" control frame в обе стороны
4. **"CLOSED" state** — TCP connection terminated

```html
<html>
    <head>
        <script>
            const webSocket = new WebSocket('ws://localhost/echo');

            webSocket.onopen = event => {

                webSocket.send("Hello Web Socket!");
            };

            webSocket.onmessage = event => {
                alert('onmessage, ' + event.data);
            };

            webSocket.onclose = event => {
                alert('onclose');
            };
        </script>
    </head>
    <body>
    </body>
</html>
```
